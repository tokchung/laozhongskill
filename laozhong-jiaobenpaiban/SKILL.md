# 脚本排版流程

> 分类：08-场景编排 | 编号：S46 | 创建：2026-08-27 | 来源：2026.8.25–8.27 两个脚本实战整理
> 最近更新：2026-11-02（新增铁律 9「非必要不硬删」、铁律 10「第一步必须是整理」、④ 查拗口、子序列校验、「用户重写回来」场景；阶段由五个扩到六个）

---

## 触发场景

- 老钟发录音转文字的脚本，要求"整理 / 清理 / 排版"。
- 触发词：「清理一下」「排版」。

## 核心铁律（全程不可违反）

1. **只清理、只排版，绝不润色**——清理 = 去口头禅、去废话、收紧啰嗦；排版 = 更有逻辑、更简洁。不动观点、不改原意、不加料、不美化措辞（删的只有口头禅和废话，其余原话保留）。
2. **不改时长**——即使偏长（如 7–8 分钟），也只排版、不删减。
3. **排版前先定位对脚本原文**——语音转文字可能误听（例：「双标」被转成「商标」），用 Grep/Read 溯源确认，不要凭空假设。
4. **字数一律用 Python 数，口径 = 含标点、不含空格**——老钟说的「字数」= 去掉全部空白、**保留标点**后的字符数（对齐 WPS 的「字符数(不计空格)」）。**禁用 `wc -m`**，原因见踩坑记录。
5. **「不要改结构」= 保留开头的留存设计，不等于把新内容堆在末尾**（2026-09-20 定性）。老钟原话：「开头不改，是因为开头是让用户更好停留的这个部分结构不改动，**并不代表说你要增加的内容不加入到这个结构里面去**，我更需要的是一种叫**融合**……**而并不是在最后融进去**。」
   - **「补」**＝在原文后面加新段落 → 前后失衡（故事轻、理论重，说教感重）
   - **「融」**＝新内容长进原有段落里 → 原段落全部保留原位、顺序不变，部分段内生长，其余插在其间
   - **自检法**：用脚本核对「原 N 段 → 新版第 M 段」的落位与长度增减（原长/现长/+N），确认**顺序未变、分布均匀**。落位全在末尾＝做成了加法，返工。
6. **替换现成例子，用「增」不用「换」**（2026-09-20 用户拍板）。原句里的例子是资产，要「换一种例子但同样的意思、同样的表达方式」时——
   - **优先在原例子后加同构第三例**（句式骨架一个词不动），比替换更稳，也加固论证
   - **加的约束**：新例子必须仍是「**熟悉的坏**」，不能变成「刺激的坏」——原句的准头在"总会不自觉被吸引"，是熟悉感在拉人，不是刺激在拉人，加错机制就偏了
   - 若"加"会顶出标题/开头限定的人群，就在原人群范围内换一种毛病（如把"被溺爱"换成"要看父亲脸色"），别改人群
7. **措辞改完才出「定稿」，定稿才交付**（2026-10-16 立、2026-10-20 加严）。老钟原话：「**以后走这个 skill 的时候必须要把措辞选择走完再定稿**」；10-20 再补一句：「**一定要改好措辞之后再定稿**」。
   - 顺序锁死：① 清理 → ② 列措辞清单 → **停下来等点选** → ③ 改 → ④ 查拗口 → ⑤ 查矛盾 → ⑥ 出定稿 → 发群
   - **禁止**：列完清单不点选就直接出「定稿」；**清理版发群**（10-20 起取消，「注明措辞待点选就能发群」的旧做法作废）
   - 群里**只出现定稿**，一次一版；清理版只落本地，给老钟点选用
   - **判据**：没走过点选那一轮，文件不许叫「定稿」，**也不许发群**
8. **先分清这份稿子是「看的」还是「听的」再谈排版**（2026-10-15 用户定性）。老钟原话：「**我这是一个口播，是我录的视频，用户是在听，他不是在看**。」
   - **对「看」**：段落粒度、字幕断行、段均字数、完读率
   - **对「听」**：顺序、**根因是否跟得住现象**、视角切换次数。口播线性、**不能回看**——听的人翻不回去，**归因必须紧跟现象**，不能隔几百字再回头补
   - 口播稿的段落切分、字幕断行**对听的人不可感**，别拿「文字墙／完播率」当理由去切段
9. **非必要不硬删**（2026-11-02 立）。老钟原话：「**不是非必要的就不用整理出来硬删了，记住**」。
   - 清理只动四类：**同一句话说两遍 / 语义讲不通 / 念出来卡住 / 跟上下文的因果对不上**。这四类之外，不列、不删
   - **可删可不删的，不要整理成清单**。硬凑一份「还能再删的地方」让用户取舍，不是交付，是把活推回去
   - 判据一句话：**删掉这处，对方会少拿到信息、或者前后因果会断——那就留着**
   - 「还能再压一点」只在用户明确要缩字数时提，并且要同时说清代价
   - 同一条已写入 `桌面\脚本整理\AGENTS.md` 第九节
10. **第一步永远是 ① 整理，不许从措辞开始**（2026-11-02 用户定）。老钟原话：「**第一步必须得是整理。因为脚本是由我录音转成文字的，那么在转换的过程中肯定是会有搞错的时候，会错意的时候，或者整理出错的时候**」。
   - 转写底稿**天然不可信**：同音错字（双标→商标、贤妻→前妻）、断句断错、漏字、把一句话拆成三截
   - 底稿没整理好就往下查，②–⑥ 全部建在错的本子上——查出来的问题也是错的，白做一轮
   - 所以 `① 清理` 和 `③ 改措辞` **不许调换**。用户临时说"先看措辞"也不行，必须先过 ①
   - ① 里遇到读不通、明显转写崩掉的地方，**单独列出来问原话，不要自己猜**

**数字数（固定口径，直接跑这个）**：

```python
txt = open(脚本路径, encoding="utf-8").read().replace("\n", "")
n = sum(1 for c in txt if not c.isspace())
print(n)
```

报数时只报这一个数。要对齐旧口径（不含标点）再单独说一个字，别混着报。

> ⚠️ **本机怎么跑这段 Python**（2026-10-01 实测补）：
> - `python` / `python3` 两个命令**指向 Windows Store 占位符，调用直接 `exit 9009`，别用**
> - **用 `py` 或 `python3`**（Windows 上 `python` 可能是 Store 占位符，报 9009 就换 `py`）
> - 例：`py -c "txt=open(r'C:\路径\脚本.md',encoding='utf-8').read().replace(chr(10),''); print(sum(1 for c in txt if not c.isspace()))"`
> - **DSH 侧没有 `py` 也没关系，用 Node 等价**（口径完全一致，只是不数空白）：
>   `node -e "const fs=require('fs');const t=fs.readFileSync(process.argv[1],'utf8');console.log(t.replace(/\s/g,'').length)" 脚本路径`
> - **口径不变**：含标点、不含空格。换工具不换口径。

> 2026-09-16 口径变更：早前定的是「不含标点」，9/16 老钟拍板改为「含标点」（跟他在 WPS 上看到的数一致，不用换算）。两个口径对同一篇稿子差约 10%（标点占比），报错口径会被当场发现。

## 六个阶段

### ① 清理排版（录音转文字的初排）

**这一步是整条流程的地基**（铁律 10）：把手机录音转出来的底稿校成一份**可信的文本**，后面 ②–⑥ 全建在它上面。底稿不可信，后面查什么都是错的。

做四件事，只清理不润色：
1. 去口头禅和废话（"然后""就是""那么"等）
2. 收紧啰嗦表达，让句子更简洁
3. 理顺逻辑顺序，让内容更顺、更有逻辑（顺序有调整，单独报）
4. 排版：一句话一行、段落之间空一行

**转写崩点单独列**：念不通、明显掉字、句子塌成一堆碎片的，整理时标出来**问原话**，不自己补、不自己猜。这类地方猜错一次，后面全跟着错。

**清理完必须跑子序列校验**（2026-11-02 立，比人工核 diff 硬）：

把原文和清理版的标点、空白全剥掉，清理版必须是原文的**子序列**——只许删，不许增，出现一个新增字直接断言失败。

```python
i = 0
for ch in orig_core:            # 原文剥掉标点空白后
    if i < len(new_core) and ch == new_core[i]:
        i += 1
assert i == len(new_core), "存在新增内容，不是纯删除 line=%d" % i
```

再把所有删除块连同上下文列出来，逐条给老钟看，允许逐条否掉。**「删了什么」要能一条一条摊开**，不能说"整体清理过了"。

### ② 查措辞（结合上下文）

- 查错别字（语音误识别，单独列，如"特么的自我"→"太自我"）
- 分工：① 只标「念不通、塌成碎片」的崩点，**逐字纠错统一放在这一步做**，别两处重复报
- 查措辞问题，四类：用词不准 / 搭配不自然 / 重复冗余 / 表达不清
- **铁律：必须结合上下文，不单句硬对**

### ③ 改措辞（老钟点选）—— ⛔ **硬停顿点**

- 措辞问题编号列出，老钟点选（如"改二四五"）才动
- 只改点选的，其余不动
- ⛔ **列完清单必须停下来等点选**（铁律 7）。不许「先把 ⑤ 矛盾核查、⑥ 落盘发群做完，顺便群也发了」——点选这一轮没走完，**不许产出「定稿」**。
- **错别字也单独列、不要顺手改**：语音误识别（如「真相**确**是」→「真相**却**是」）同样要报出来等点头，别夹在 ① 清理里做掉。2026-10-15 这么干过两处，用户的反馈是「**是该措辞这一环节你没有问我**」。
- ⛔ **这一步不发群**：清理版只落本地文件，等老钟点选；发群是 ⑥ 的动作，点选没走完不发。
- **顺序不可调**：`① 清理` 必须是第一步，和 ③ 不许对调（铁律 10）。理由见铁律 10——转写底稿不可信，没整理过就查措辞，等于在错的本子上挑错字。

### ④ 查拗口（按「念」扫，不按「词」扫）

和 ② 是两件事：② 按词扫（用词准不准、搭配顺不顺），④ 按念扫（**能不能一口气念下来**）。2026-11-02 实测：④ 抓出的 7 处「会卡」，② 那轮按词扫**全漏了**，包括全篇最硬的一句病句「你就相对应的你要去承受」。

查五类：

1. **虚词堆叠**：连续几个虚词，中间没有实词落点（「很可能反而」「可以…在…去」）
2. **两字连读拗口**：前后两个字撞在一起念不顺（「伤害**你你**都没有」「帮助**跟爱他就**一定要接受」）
3. **主语中途换人**：前一句是宾语、后一句变主语，中间只有逗号（「…给男朋友更多的包容，耐心引导男朋友也是属于那种…」）
4. **引号／短句后无停顿**：一句收不住，和下一句黏成一串
5. **同段同一个词连用**：如一段里「更痛苦」出现四次

输出分两档，**会卡的**和**拗但能念的**分开列，每条给「原句｜问题｜改法」，编号等点选。用户通常全选第一档、不动第二档。

### ⑤ 查前后矛盾（结合因果）

- **铁律：看上下文的因果关系，不能抽单句对比**
- 教训：因果递进 / 时间层次 / 隐含前提，单句硬对会误判成矛盾（8/25 被纠正过）

### ⑥ 落盘验证

- **前置检查（铁律 7）**：③ 的点选走完了吗？**没走完 → 不出定稿、不发群**，清理版只落本地等点选。「先发清理版、注明不是定稿」这条路 2026-10-20 起关闭。
- **发群一次一版**：回退／改动的决定全部做完再发。同一个文件名发两次内容不同的稿子 ＝ 群里分不清哪份有效（2026-10-15 翻过车，最后靠补一条作废说明才收口）。
- 定稿版与清理版**用不同文件名**（`-清理版-日期.md` / `-定稿-日期.md`）；**进群的只有定稿**，说明里点一句「以本定稿版为准」。
- Write 后确认文件真实存在 + 查字数（口径见核心铁律 4，用 Python 数，不用 `wc -m`）
- 教训：只贴路径和正文、没执行写入，文件根本不存在（8/25 翻过车）
- **改过的脚本直接交给用户**（纠错／改稿／重组／定版一律交，不用问「需要发吗」）

## 特殊情况：老钟自己重写了一遍

**场景**：流程走到一半（清理完、或措辞刚改完），他直接发回一份自己重写过的 docx——换掉整个案例、重写某个段落、补新句子、加结尾金句。

**不要**继续套清理流程重跑一遍，那等于把他写的东西又洗一次。正确动作是**逐句对比复核**，分三档交付：

1. **硬伤**（念出来会卡、语义讲不通）：错字、主语丢失、两个「你」撞一起、引号后无停顿、段末缺句号。**给改法，他一般全改。**
2. **偏**（读得懂，但那层意思挪位了）：如「他就不**需要**改变」vs「不**会**改变」、「你把他当成了你」。**只指出、给备选，让他定；他大概率不改。**
3. **因果**（这段还成不成立）：新换的案例，证明的是上一段立的那条因果吗？还是另起了一条？两段是**递进**还是**并列**？——这一条最容易漏，也最影响成篇。

**同时要动的两件事**：
- 报字数变化（原稿 → 他重写后），并说清"这版长度是内容多还是废话多"
- 检查他的新内容有没有顶掉前面的呼应（如结尾金句删了，开头的引句就没人回扣）

2026-11-02 实测：他重写到 2443 字，查出 6 处硬伤 + 3 处「偏」+ 1 处案例因果不承接（案例二从「投射」变成「撤出」，跟上一段立的因果不是一条线）。
